# Specification

ERC-8128 uses RFC 9421 HTTP Message Signatures with Ethereum accounts.

- Key identifiers are canonical `eip155:<chain-id>:<lowercase-address>` CAIP-10
  strings.
- Direct signatures carry `tag="erc8128"`; delegated requests and grants use
  their dedicated mandatory tags.
- Request-bound signatures cover `@scheme`, `@authority`, `@method`, `@path`,
  and `@query`. Received content requires Content-Digest coverage and exact-byte
  RFC 9530 verification; received Content-Type must also be covered.
- Component identifiers are structural and support all RFC 9421 component
  parameters. Dictionary-valued fields with `;sf` are canonicalized according
  to RFC 9651 before signing or verification.
- Non-replayable signatures carry a bounded nonce that the verifier consumes
  atomically only after all other checks pass.
- Direct accounts are verified universally through ERC-6492, ERC-1271, or
  strict low-s EOA recovery. Verification transport failure is distinct from an
  invalid signature.

The closed delegation Dictionary binds root and delegate CAIP-10 identities,
one to sixteen exact RFC 6454 audience origins, a 32-byte identifier, issuance
epoch, time and replay posture, additional component requirements, and optional
standard scopes. `allow-replayable=?1` permits but does not default requests to
replayable; absence requires a nonce. Unknown members, wildcards, credentials,
paths, opaque origins, and insecure non-loopback origins are rejected.

Delegated verifiers pin the trusted revocation registry and chain in policy.
The signer cannot select them. The verifier checks root, authorization id, and
issuance epoch against that authority before nonce consumption.

RFC 9457 helpers encode authentication failures. Invalid proof is normally 401,
authenticated principals missing application authorization are 403, and
unavailable signature or revocation verification is retryable at 503.
